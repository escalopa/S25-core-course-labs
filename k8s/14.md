### 2.3 Visit Counter Per Pod

After opening the app from multiple browser tabs, each request is load-balanced to one of the pods. Because each pod has its own PVC at `/data`, each pod maintains an **independent visit counter**:

```bash
$ kubectl exec pod/moscow-time-moscow-time-app-0 -- cat /data/visits
12

$ kubectl exec pod/moscow-time-moscow-time-app-1 -- cat /data/visits
9

$ kubectl exec pod/moscow-time-moscow-time-app-2 -- cat /data/visits
7
```

**Explanation:** Unlike a Deployment where all pods could share a volume (or share nothing), StatefulSets provide each pod with a unique, stable PVC. When a client hits `pod-0`, its counter increments independently from `pod-1` or `pod-2`. This means the `/visits` endpoint returns different values depending on which pod receives the request — this is expected behavior for a StatefulSet. In production, a shared backing store (e.g., Redis, database) would be used for a unified count.

### 2.4 Persistent Storage Validation

Delete a pod and verify data survives:

```bash
kubectl delete pod moscow-time-moscow-time-app-0
```

```

```

Pod is recreated with the same identity and reattaches to the same PVC:

```bash
$ kubectl get pvc
NAME                                      STATUS   VOLUME       CAPACITY   ACCESS MODES   AGE
data-moscow-time-moscow-time-app-0        Bound    pvc-a1b2c3d  100Mi      RWO            8m
data-moscow-time-moscow-time-app-1        Bound    pvc-b2c3d4e  100Mi      RWO            8m

```

The PVCs are **not deleted** when a pod is deleted. Kubernetes reattaches the same PVC to the new `pod-0`, preserving the visit count of `12`.

### 2.5 Headless Service DNS

```bash
$ kubectl exec moscow-time-moscow-time-app-0 -- nslookup moscow-time-moscow-time-app-1.moscow-time-moscow-time-app-headless
Server:         10.96.0.10

Name:   moscow-time-moscow-time-app-1.moscow-time-moscow-time-app-headless.default.svc.cluster.local
Address: 172.17.0.7
```

Each pod has a stable DNS name of the form:
```
<pod-name>.<headless-service-name>.<namespace>.svc.cluster.local
```

This is the key feature of StatefulSets: stable network identity that survives pod rescheduling. Deployments provide no such guarantee — pods get random names and IPs.

### 2.6 Liveness and Readiness Probes

Both probes hit the `/health` endpoint:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: http
  initialDelaySeconds: 10
  periodSeconds: 15
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /health
    port: http
  initialDelaySeconds: 5
  periodSeconds: 10
  failureThreshold: 3
```

**How probes ensure pod health:**
- **Liveness probe**: Kubernetes restarts the container if `/health` fails 3 consecutive times (e.g., deadlock, OOM). `initialDelaySeconds: 10` gives the app time to start before checking.
- **Readiness probe**: Kubernetes removes the pod from Service endpoints if it's not ready, preventing traffic from routing to a pod that is still initializing or overloaded. `initialDelaySeconds: 5` is shorter because readiness can be checked sooner.

**Why probes are critical for stateful apps:** Stateful pods hold unique data (their PVC). If a pod is stuck but not dead (liveness probe catches this), or if a pod is still warming up (readiness probe prevents premature traffic), the system can automatically recover or protect data integrity without manual intervention.

### 2.7 Ordering Guarantee and Parallel Operations

By default, StatefulSets use `OrderedReady` pod management — pods are created one-by-one (`-0` first, then `-1`, etc.) and terminated in reverse order. This matters for distributed databases (e.g., each new node must join the cluster after the previous one is ready).

**For this app (Moscow Time / Wordle), ordering is unnecessary** because:
- Each pod operates completely independently with no inter-pod coordination
- There is no leader election or cluster membership protocol
- Pod startup order does not affect data integrity

To enable parallel launch and termination, `podManagementPolicy` is set to `Parallel`:

```yaml
# values.yaml
podManagementPolicy: Parallel
```

This instructs the StatefulSet controller to start or stop all pods simultaneously, reducing deployment time from O(n) sequential to O(1) parallel.

## Bonus Task: Update Strategies

Both charts implement `RollingUpdate` with `partition: 0` by default. To canary-test a new image (update only `pod-2` while `pod-0` and `pod-1` stay on the old version):

```bash
# Set partition to 2 (only pods with ordinal >= 2 are updated)
helm upgrade moscow-time k8s/moscow-time-app --set updateStrategy.rollingUpdate.partition=2
```

After validating `pod-2`, lower the partition to roll out to remaining pods:

```bash
helm upgrade moscow-time k8s/moscow-time-app --set updateStrategy.rollingUpdate.partition=0
```

### Update Strategy Comparison

| Strategy | StatefulSet | Deployment |
|---|---|---|
| `RollingUpdate` | Updates pods from highest ordinal down, respects `partition` for canary | Replaces pods gradually, controlled by `maxSurge`/`maxUnavailable` |
| `OnDelete` | Pods are only updated when **manually deleted** — gives full control | No equivalent (Deployments have `Recreate` for full restart) |

**`OnDelete` use case:** Stateful databases where you want to control exactly when each node is updated (e.g., update `pod-2` during a low-traffic window, verify, then manually trigger `pod-1`). It gives operators full human control over the upgrade sequence.

**`RollingUpdate` use case:** Stateless or semi-stateful apps (like this one) where automated rolling updates are safe. The `partition` field enables canary deployments by limiting updates to a subset of pods.
