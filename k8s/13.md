# Lab 13: ArgoCD for GitOps Deployment

## Overview

Lab 13 implements ArgoCD to automate Kubernetes application deployments using GitOps principles. ArgoCD is installed via Helm and configured to manage the Python (Moscow Time) and Go (Wordle) applications across multiple environments.

### 1.4 Configure Python App Sync

**Created: `k8s/ArgoCD/argocd-python-app.yaml`**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: python-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/escalopa/S25-core-course-labs.git
    targetRevision: lab-13
    path: k8s/moscow-time-app
    helm:
      valueFiles:
        - values.yaml
  destination:

    namespace: default
  syncPolicy:
    automated: {}
```

### 2.6 ArgoCD Drift vs. Runtime Events

| Scenario | Who Handles | ArgoCD Drift? |
|---|---|---|
| Manual replica patch | ArgoCD selfHeal reverts | ✅ Yes — drift detected, reverted |
| Pod deleted | Kubernetes Deployment controller recreates | ❌ No — individual pods are not part of desired state |
| ConfigMap/Deployment YAML changed manually | ArgoCD selfHeal reverts | ✅ Yes — drift detected, reverted |

**Explanation:**

ArgoCD manages *desired state* at the Kubernetes resource level (Deployments, Services, ConfigMaps, etc.). When a Deployment's `spec.replicas` is manually changed, ArgoCD detects this as configuration drift against the Git source and reverts it (because `selfHeal: true` is set).

Pod deletions, however, are handled entirely by the Kubernetes Deployment controller — it reconciles the running pod count against `spec.replicas`. ArgoCD is not involved and sees no drift, because the Deployment manifest itself has not changed.
