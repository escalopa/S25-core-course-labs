## Task 1: Kubernetes Cluster Monitoring with Prometheus

### 1.1 Kube Prometheus Stack Components

The Kube Prometheus Stack is a Helm chart that bundles several tightly integrated monitoring tools:

| Component | Role |
|---|---|
| **Prometheus** | Time-series database and scrape engine. Pulls metrics from configured targets (pods, nodes, kubelets) via HTTP, stores them, and evaluates alerting rules. |
| **Alertmanager** | Receives alerts fired by Prometheus rules, de-duplicates them, and routes notifications to receivers (email, Slack, PagerDuty, etc.). |
| **Grafana** | Visualization layer. Reads data from Prometheus and renders dashboards. The chart ships pre-built dashboards for cluster health, node metrics, workload views. |
| **kube-state-metrics** | Reads Kubernetes API objects (Deployments, Pods, StatefulSets, PVCs) and exposes them as Prometheus metrics (e.g., `kube_pod_status_ready`). Prometheus itself knows nothing about Kubernetes objects — kube-state-metrics bridges that gap. |
| **node-exporter** | DaemonSet running on every node. Exposes OS-level hardware metrics (CPU, memory, disk I/O, network) from each node to Prometheus. |
| **Prometheus Operator** | Kubernetes controller that manages Prometheus and Alertmanager instances via CRDs (`ServiceMonitor`, `PrometheusRule`). Instead of editing Prometheus config files, you create Kubernetes objects, and the operator reconciles them into a running Prometheus config. |

### 1.2 Install the Stack

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --version 57.2.0
```

Install the app chart:

```bash
helm install moscow-time k8s/moscow-time-app
```

## Task 2: Init Containers

### 2.1 Implementation

**Updated: `k8s/moscow-time-app/templates/statefulset.yaml`**

Added `initContainers` block and an `init-work` emptyDir volume:

```yaml
initContainers:
  - name: init-downloader
    image: busybox:1.36
    command:
      - wget
      - "-O"
      - /init-work/test.html
      - "http://info.cern.ch"
    volumeMounts:
      - name: init-work
        mountPath: /init-work
  - name: init-line-1
    image: busybox:1.36
    command: ["sh", "-c", "echo 'Init container 1 ran at '$(date) >> /init-work/init.log"]
    volumeMounts:
      - name: init-work
        mountPath: /init-work
  - name: init-line-2
    image: busybox:1.36
    command: ["sh", "-c", "echo 'Init container 2 ran at '$(date) >> /init-work/init.log"]
    volumeMounts:
      - name: init-work
        mountPath: /init-work
  - name: init-line-3
    image: busybox:1.36
    command: ["sh", "-c", "echo 'Init container 3 ran at '$(date) >> /init-work/init.log"]
    volumeMounts:
      - name: init-work
        mountPath: /init-work
```

The `init-work` volume is an `emptyDir` shared between all init containers and the main container (mounted read-only in the main container at `/init-work`).

**New `values.yaml` fields:**

```yaml
initContainers:
  enabled: true
  downloadURL: "http://info.cern.ch"
```

### Bonus 2: Init Container Queue Proof

All three init containers write to the same `/init-work/init.log` file in sequence. Because Kubernetes runs init containers **sequentially** (each must complete before the next starts), the log always shows them in order:

```bash
$ kubectl exec pod/moscow-time-moscow-time-app-0 -- cat /init-work/init.log
Init container 1 ran at Sun Feb 22 10:15:03 UTC 2026
Init container 2 ran at Sun Feb 22 10:15:04 UTC 2026
Init container 3 ran at Sun Feb 22 10:15:05 UTC 2026
```

The timestamps confirm sequential execution — each container starts only after the previous one has exited with code `0`. If any init container fails, Kubernetes restarts it (and does not start subsequent init containers or the main container) until it succeeds, respecting the `restartPolicy`.
